## 一、项目背景

### 1.1 三十秒讲清（面试开场直接用这段）

> 电商售后最贵的不是响应慢，是**判责不一致**。同样一张退货工单，客服 A 说能退，客服 B 让补证据，客服 C 直接拒了；用户一申诉，二线复核推翻一线的比例能到十几个百分点。这背后是三笔真金白银的账：重复沟通的工时、错赔出去的钱、用户被反复折腾后的流失。而这个问题加人解决不了，因为人会疲劳、会有个体差异。
>
> 所以我做的不是"会聊天的客服"，是一套判责引擎：把法律和平台规则写成可执行的规则，让规则处理掉大部分确定性场景，模型只在规则留白的地方补语义理解，最后产出的不是一段话术，而是一张带依据条款、退款金额和置信度的判定单。

这段话包含四个要素，缺一个就立不住：**反常识的判断**（不是响应慢）、**可感知的损失**（推翻率）、**堵死廉价解**（加人没用）、**落到产物**（判定单而非聊天框）。

### 1.2 两分钟展开版

如果面试官说"具体讲讲"，按四层铺开：

**第一层，现象。** 售后是高频、长尾、强规则的场景。日均几百条会话，七成能归入十来个意图，每个意图的判定都受平台规则约束——能不能退、退多少、谁承担运费，不是客服能自由裁量的。

**第二层，问题。** 同一类诉求经常得到不同结论。原因不是客服不专业，是规则太多太散，人记不全，也执行不稳。

**第三层，为什么现有方案绕不过去。** 关键词机器人只能分流不能判断；纯大模型方案更糟——同一张工单问两次能给两个答案，还会编造政策条款、顺着用户的意思判。**判定这件事的确定性需求，和概率模型的本质是冲突的。**

**第四层，解法。** 把规则和语义拆开：规则负责确定性判定，模型负责理解用户到底在说什么，中间加一层仲裁，规定冲突时谁说了算。最终产物是结构化判定单，可以入库、抽检、对账。

### 1.3 问题的成本结构

把"判责不一致"拆开，它同时产生三类成本，且互相放大：

| 成本类型 | 具体表现 | 谁承担 |
|---|---|---|
| 效率成本 | 用户重复描述、客服反复查证、二线复核 | 商家与用户共同承担 |
| 赔付成本 | 该拒的判了退，直接现金损失 | 商家 |
| 信任成本 | 同一问题两次得到不同答复，用户流失 | 商家（延迟体现） |

三者中**赔付成本是即时可见的，信任成本是延迟且不可逆的**。这决定了系统的取舍：宁可多转人工，也不能错判，因为错判的代价不对称。这句话能解释后文所有阈值设计为什么偏保守。

### 1.4 现有方案为什么都解决不了

| 方案 | 优势 | 为什么解决不了 |
|---|---|---|
| 人工客服 | 灵活，能处理复杂纠纷 | 一致性靠人维持，必然随疲劳与个体差异波动 |
| 关键词/菜单机器人 | 成本极低、完全可控 | 只能做固定分流，无法处理自然语言表达 |
| 纯 Prompt 大模型 | 上手快、表达自然 | 结论不稳定、编造政策、倾向顺着用户、无边界 |
| 多智能体编排 | 理论上可覆盖全流程 | 本任务链路线性，多角色反而引入上下文不一致 |

纯大模型方案的四个缺陷值得单独列出，因为这是本项目存在的根本理由：

| 缺陷 | 具体表现 | 后果 |
|---|---|---|
| 结论不稳定 | 同一工单两次调用给出不同判定 | 无法审计，无法对账 |
| 无依据 | 编造不存在的政策条款 | 合规风险 |
| 不会拒 | 倾向于顺着用户意思给结论 | 过度赔付 |
| 无边界 | 遇到未定义情况自由发挥 | 不可控 |

**结论：售后判责是"规则密集 + 需要语义理解"的混合任务。规则部分必须确定性执行，语义部分才交给模型。**

### 1.5 项目价值

价值要分对象说，笼统讲"提升效率"没有说服力。

**对商家（业务价值）**

| 价值点 | 具体含义 | 可衡量方式 |
|---|---|---|
| 判定一致性 | 同一工单必得同一结论，消除个体差异 | 同输入重复调用的结果一致率 |
| 结论可审计 | 每条判定挂在具体条款编号上，事后可查 | 判定单的 `policy_refs` 覆盖率 |
| 成本结构优化 | 大部分工单不调用模型，token 与延迟同步下降 | 规则覆盖率、单票平均成本 |
| 风险可控 | 大额强制人工，模型无权产生判定结论 | 越权判定数（设计上应为 0） |

**对用户（体验价值）**：不用重复描述问题、不用看客服心情、不会两次得到两种答复。售后体验的核心不是"态度好"，是**结论说得准、说得算**。

**对技术本身（可迁移的模式）**：这个项目真正沉淀下来的不是一套售后规则，而是一个可复用的模式——**当业务要求确定性、而自然语言理解必须依赖概率模型时，怎么在两者之间划边界**。同样的模式可以迁移到保险理赔、信贷审批、合规审核，所有"有规则但规则说不全"的场景。

**对求职者（证明了什么能力）**

| 能力 | 体现在哪 |
|---|---|
| 业务建模 | 把模糊的政策文本拆成 12 条可执行、可测试的规则 |
| 架构判断力 | 知道哪些环节必须确定性、哪些可以容忍概率，并说清理由 |
| 工程完备性 | 有分层评测、有置信度推导、有数据校验，不是跑通就算完 |
| 技术诚实 | 能说清方案边界与指标局限，而不是宣称"准确率 99%" |

### 1.6 与常见同类项目的区别

绝大多数同类项目的形态是"用户提问 → 模型调工具 → 模型说一段话"，产物是一个聊天框。本项目产物是一份判定单：

```json
{
  "ticket_id": "T-ORD10001",
  "order_id": "ORD10001",
  "decision": "SUPPORT_RETURN",
  "decision_label": "支持退货",
  "refund_amount": 328.0,
  "shipping_bearer": "BUYER",
  "policy_refs": ["R-101", "R-301"],
  "confidence": 0.95,
  "decided_by": "RULE_ONLY",
  "need_human": false,
  "reason": "签收次日起 2 天，在七天无理由期内，商品未拆封、非例外类目，可退 328.00 元，寄回运费由买家承担。"
}
```

（以上为真实运行输出。）这个产物可以入库、可以对账、可以抽检、可以统计准确率。**它是个数据产品，不是个聊天框。**

## 二、目标与边界

### 2.1 业务目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 判责准确率 | ≥ 90% | 与人工标注结论一致 |
| 误赔率 | ≤ 3% | 不该退却判退 |
| 误拒率 | ≤ 5% | 该退却判拒 |
| 规则覆盖率 | ≥ 55% | 无需调用模型即可判定的工单占比 |
| 越权判定数 | 0 | 模型不产生判定结论，由架构保证 |
| 大额自动退款数 | 0 | 金额 ≥ 2000 元一律人工 |

### 2.2 技术目标

- 判定逻辑可单测、可复现：同一输入必得同一输出。
- 判定过程全程可观测：每轮决策、工具入参出参、置信度来源均可回溯。
- 评测可回归：固定用例集，每次改动可对比指标涨跌。
- 降级可用：模型或网络不可用时，规则引擎仍能独立完成大部分判定。

### 2.3 明确不做的事

清晰的边界是项目可信度的前提。本项目**不处理**：

- 改价、补差价、发放优惠券等涉及资金定价的操作。
- 投诉升级、平台介入、法律纠纷类会话。
- 主动营销、催付、挽回等售前运营动作。
- 图片/视频证据的视觉质检（仅做转人工触发，不做自动判责）。

上述请求一律走「识别 → 说明 → 转人工」路径。

## 三、核心架构：Rule-first, Model-fallback

### 3.1 架构总览

```
              ┌─────────────────────────────┐
   工单输入 → │ ① 事实层：订单/物流/售后记录  │  确定性查询
              └──────────────┬──────────────┘
                             ▼
              ┌─────────────────────────────┐
              │ ② 规则层：规则引擎（12 条）   │  确定性判定
              └──────────────┬──────────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
      命中硬规则                    规则未覆盖/存在争议
              │                             │
              │                             ▼
              │              ┌─────────────────────────────┐
              │              │ ③ 语义层：LangChain + LLM    │
              │              │    意图识别 / 类目归属 / 表述  │
              │              └──────────────┬──────────────┘
              │                             ▼
              │              ┌─────────────────────────────┐
              │              │ ④ 仲裁层：冲突检测 + 置信度   │
              │              └──────────────┬──────────────┘
              │                             │
              └──────────────┬──────────────┘
                             ▼
              ┌─────────────────────────────┐
              │ ⑤ 输出层：结构化判定单        │
              │    低置信 → 人工复核队列      │
              └─────────────────────────────┘
```

### 3.2 这个架构解决什么

**规则优先**保证一致性与可审计性：同一工单必然得到同一结论，且结论可以指向具体条款。
**模型兜底**解决规则不可能穷举所有自然语言表达的问题。
**仲裁层**是二者之间的宪法，规定冲突时谁说了算。

工程上三个直接收益，都可量化：

1. **成本下降**：约 60% 的工单不需要调用大模型，token 成本与延迟同步下降。
2. **可测试**：规则层可单元测试，不需要跑模型就能验证判定逻辑。
3. **可迭代**：模型判错的案例记入冲突日志，反向驱动规则补充，系统越用越"重规则、轻模型"。

**一个来自实测的佐证**：规则引擎在 2000 条样本上判定全部正确后，唯一的错误来源是意图识别——用户说"杯口崩了"，关键词表里只有"崩瓷"，整条判定落到兜底转人工。**判定逻辑没有错，错在语义理解。** 这正是分层架构的价值：每一层出的问题，可以明确归因到那一层。

## 四、规则层设计

### 4.1 规则清单

完整规则文本见 `data/policies.md`（每条标注法规或平台规则出处）。代码实现于 `core/rules.py`。

| 编号 | 规则内容 | 类型 | 优先级 |
|---|---|---|---|
| R-601 | 政策咨询：只问通用规则、不针对具体订单 → 不产生判定结论 | 硬规则 | 1 |
| R-501 | 幂等约束：已退款或已有进行中工单不可重复受理 | 硬规则 | 2 |
| R-502 | 已关闭订单：已取消 / 交易关闭 / 待付款，无售后标的 | 硬规则 | 3 |
| R-505 | 金额异常：实付金额缺失或 ≤ 0，无法计算退款 → 转人工 | 硬规则 | 4 |
| R-402 | 大额阈值：单笔 ≥ 2000 元必须人工复核 | 硬规则 | 5 |
| R-503 | 物流争议：已签收但用户主张未收到货，签收事实存疑 | 硬规则 | 6 |
| R-102 | 例外类目：生鲜、定制、拆封个护、激活数码、贴身衣物，不适用无理由 | 硬规则 | 7 |
| R-201 | 未发货：诉求为取消/无理由时全额退款；催发货不退款 | 硬规则 | 8 |
| R-202 | 在途：提出退货/拒收才引导拒收退款；纯物流查询转人工，不产生账务动作 | 硬规则 | 9 |
| R-105 | 超期拒收：距签收超过 30 日不再受理 | 硬规则 | 10 |
| R-103 | 质量问题退货：签收 30 日内，有凭证支持退货，无凭证转待补充 | 硬规则 | 11 |
| R-104 | 质量问题换货：签收 15 日内 | 硬规则 | 11 |
| R-101 | 七天无理由：签收次日起 7 个自然日内，非例外类目、商品完好 | 硬规则 | 12 |
| R-106 | 超无理由期：8–30 天 + 无理由 → 拒绝，主张质量问题仍可申请 | 硬规则 | 13 |
| R-504 | 兜底：诉求无法匹配任何规则 → 强制转人工，不产生账务动作 | 硬规则 | 14 |
| R-203 | 已签收：进入签收类判定，不独立产生结论 | 说明性 | — |
| R-301 | 运费承担：无理由买家承担，质量问题卖家承担 | 说明性 | — |
| R-401 | 退款时效：原路退回，验收后 1–3 个工作日 | 说明性 | — |

**口径说明**（实现时最容易出错的地方，规则库中已固定）：

- 距签收天数：签收当日记第 0 天，次日为第 1 天。
- 优先级在前的规则一旦命中，直接采纳结论，不再进入后续规则。
- 例外类目**仍适用质量问题退换**：用户主张质量问题的，不适用 R-102，改按 R-103。

### 4.2 判定优先级（仲裁顺序）

```
R-601 政策咨询 > R-501 幂等 > R-502 已关闭 > R-505 金额异常
   > R-402 大额 > R-503 物流争议 > R-102 例外类目
   > R-201/R-202 未发货与在途 > R-105 超期
   > R-103/R-104 质量问题 > R-101 七天无理由
   > R-106 超无理由期 > R-504 兜底转人工
```

三条设计理由：

- **咨询与"有没有可退的标的"排在业务判断之前**：问一句"退货流程怎么走"不该收到一张"拒绝受理"；已退款、已取消的订单再讨论能不能退没有意义。
- **幂等置于最高业务规则之前**：账务正确性高于业务判断正确性。已退款的订单无论理由多充分都不能再次进入退款流程——实测中，该订单即使用户意图"未识别"，判定依然正确，因为幂等检查不依赖意图。
- **大额置于例外类目之前**：一张 5800 元的激活数码订单，同时命中 R-402 和 R-102。让资金风控优先，因为误赔的损失不可逆，而类目问题人工复核即可纠正。

### 4.3 判定结果枚举（11 个）

固定枚举是结构化的前提。判定结果只允许以下取值，不允许自由文本：

| 枚举值 | 含义 | 后续动作 | 终态 |
|---|---|---|---|
| `SUPPORT_RETURN` | 支持退货 | 创建退货工单 | 是 |
| `SUPPORT_EXCHANGE` | 支持换货 | 创建换货工单 | 是 |
| `SUPPORT_REFUND_ONLY` | 仅退款（未发货） | 直接发起退款 | 是 |
| `GUIDE_REJECT_ON_DELIVERY` | 在途引导拒收 | 拒收后退款 | 是 |
| `REJECT_OVERDUE` | 超期拒绝 | 告知理由，可申诉 | 是 |
| `REJECT_EXEMPT_CATEGORY` | 例外类目拒绝 | 告知类目规则 | 是 |
| `REJECT_DUPLICATE` | 重复申请拒绝 | 提示查询原退款 | 是 |
| `REJECT_CLOSED_ORDER` | 订单已关闭拒绝 | 提示无售后标的 | 是 |
| `NEED_EVIDENCE` | 待补充凭证 | 引导上传后重判 | **否** |
| `NEED_HUMAN` | 转人工 | 进复核队列 | 是 |
| `POLICY_ANSWER` | 政策咨询（不产生判定） | 交咨询链路作答 | **否** |

枚举定义于 `core/schema.py`，附带严格的不变量校验：拒绝类判定不得携带退款金额、支持类判定必须携带正金额、任何判定必须挂到具体规则上。校验不通过的判定单不允许流出。

### 4.4 置信度推导

置信度由判定路径推导，**不由模型自评**——模型给出的置信度不可校准、不可复现。

| 判定路径 | 置信度 | 含义 |
|---|---|---|
| 规则唯一命中（RULE_ONLY） | 0.95 | 结论由确定性规则直接给出 |
| 模型辅助补判（MODEL_ASSISTED） | 0.75 | 预留路径，当前未启用 |
| 转人工（HUMAN） | 1.0 | 表达的是"该转人工"这个判断确定，不代表结论可信 |

**为什么没有"冲突折扣"和"置信度阈值"**：设计阶段预留了这两个常量（模型结论与规则不一致时扣 0.2、低于 0.7 不得自动出结论），实现时发现它们要解决的问题不存在——模型只输出意图枚举、不参与判决，因此既不存在"模型结论与规则冲突"，也不存在"自动结论置信度不足"。规则引擎的每个分支都是确定性的：命中即结论，未命中即转人工。**留空的抽象比错误的抽象好，所以直接删掉，而不是保留成永远不生效的配置。**

好处：置信度可复现、可测试，不依赖模型输出。

## 五、数据设计

### 5.1 三层数据来源

**第一层：规则条目——真实，有出处，不需要编造**

| 规则 | 出处 |
|---|---|
| 七天无理由退货 | 《中华人民共和国消费者权益保护法》第二十五条 |
| 不适用无理由的类目 | 消法第二十五条除外情形 + 主流电商平台公开规则 |
| 质量问题退换时限 | 平台公开售后规则 |
| 运费承担 / 退款时效 | 平台公开规则 |

规则进入 `data/policies.md` 时逐条标注出处，判定结果的 `policy_refs` 引用这些编号。**每一条判定都能追溯到公开依据。**

**第二层：订单数据——合成，但按场景矩阵设计**

工业界测试数据本就是合成的，问题在于随手编的合成数据无法证明覆盖度。本项目按五维场景矩阵构造：

| 维度 | 取值 |
|---|---|
| 订单状态 | 待发货 / 已发货在途 / 已签收 / 已退款 |
| 时间（距签收） | 期内（≤7 天） / 超期（8–30 天） / 严重超期（>30 天） |
| 类目属性 | 普通 / 生鲜 / 定制 / 拆封个护 / 激活数码 |
| 金额 | 小额（<2000） / 大额（≥2000） |
| 纠纷性质 | 无理由 / 质量问题 / 物流问题 / 用户施压 |

**第三层：评测语料——公开规则改写，不抓投诉原文**

工单的诉求文本不应凭空编写，但也不能为了"真实"去批量抓投诉站。**评估后的取舍**：

| 方案 | 结论 | 原因 |
|---|---|---|
| 抓取黑猫投诉 / 12315 公示 | 放弃 | ToS 限制批量抓取与再分发；正文含个人信息；用户生成内容不当然允许转载 |
| 整包引入公开客服对话数据集（JDDC 等） | 未随仓库分发 | 多为研究用途许可，"使用"不等于"允许再分发"；仓库只提供导入器 |
| 公开法律/平台规则改写 + 人工编写话术 | **采用** | 依据公开、可标注来源、无个人信息、可复现 |

因此仓库里的评测话术分两类：**人工编写**（覆盖口语、对抗、边界）与**公开规则改写**（同一规则换不同问法，测检索稳健性）。后者带 `source_name / source_url / license` 字段，导入过程见 [`数据来源与合规说明.md`](./数据来源与合规说明.md)。

> 必须说清的边界：公开改写集的期望条款仍来自本仓库规则库，**不是独立第三方基准**，不能拿它宣称"外部数据准确率"。

### 5.2 按标签生成（label-first generation）

生成批量数据时有一个必须避开的陷阱：**如果先用规则引擎跑一遍生成"标准答案"，再用这份答案评测规则引擎，准确率永远 100%，评测失去意义。**

正确做法是按标签生成：先决定这条订单"期望被判成什么"，再反推构造满足该判定的参数（距签收天数、类目、金额、状态），最后落成订单记录。标签在构造阶段确定，与被测系统完全解耦。实现于 `tools/gen_orders.py`。

### 5.3 数据规模与分布（实测）

| 数据集 | 条数 | 性质 | 作用 |
|---|---|---|---|
| `orders.json` | 17 | gold（人工确认） | 验证规则逻辑正确性，覆盖全部 11 个判定分支 |
| `orders_bulk.json` | 1986 | silver（按标签生成） | 统计判定准确率与分支分布 |
| 合计 | 2000 | — | — |

silver 各分支分布（每分支约 69 条）：

| 判定分支 | 条数 | 距签收天数 | 金额区间 |
|---|---|---|---|
| SUPPORT_RETURN | 69 | 1–6 | 52–1499 |
| SUPPORT_EXCHANGE | 69 | 1–14 | 60–1517 |
| SUPPORT_REFUND_ONLY | 69 | 待发货 | 69–1559 |
| REJECT_OVERDUE | 69 | 33–120 | 79–1506 |
| REJECT_EXEMPT_CATEGORY | 69 | 1–6 | 62–1999 |
| NEED_EVIDENCE | 69 | 8–30 | 63–1416 |
| NEED_HUMAN | 74 | 1–6 | 2201–8589 |

**为什么是 2000 这个量级**：规则覆盖率、误赔率等都是百分比指标，百分比在样本太小时没有统计意义。总量决定整体指标的可信度，**但更关键的是单分支样本量**——11 个判定分支均分后，500 条总量下每分支仅约 50 条，分支级准确率的 95% 置信区间宽达 ±8 个百分点，写"超期拒绝分支准确率 95%"实际可能落在 87%–100% 之间，经不起追问。2000 条总量下每分支约 220 条，区间收窄到 ±4 个百分点，整体指标也达到 ±1.3 个百分点，两类指标都站得住。

**面试被问"数据量这么少能说明什么"，这样答**：这是固定评测集，不是训练集。它的作用是回归验证——2000 条均分到 9 个分支后每分支约 220 条，既能覆盖分支边界，也能让分支级指标有 ±4 个百分点以内的置信区间。生成器脚本可一键扩到任意规模，规模不是瓶颈，标注质量才是。

### 5.4 数据一致性校验

生成后全量校验，当前 0 错误：

- 金额一致性：`amount == price × qty`（允许 0.02 元舍入误差）
- 时间链：`created_at ≤ paid_at ≤ shipped_at ≤ delivered_at`，不乱序
- 状态一致性：已签收必有 `delivered_at`，待发货必无 `shipped_at`
- 例外类目必有结构化字段 `exempt_reason`，不依赖商品名做字符串匹配

校验过程中实际发现并修复过三类问题：数量为 2 时金额未乘、发货时间晚于签收时间、例外类目信息只存在于商品名中。**这类问题留到评测阶段会非常难排查，必须在数据层拦住。**

## 六、语义层与仲裁层

### 6.1 模型在这里做什么、不做什么

模型不做最终判定，只做三件规则做不到的事：

1. **诉求性质识别**：把自然语言映射到 `无理由 / 质量问题 / 物流问题 / 政策咨询` 四类。
2. **类目归属判定**：商品标题模糊时（如"进口车厘子礼盒"是否属生鲜），由模型判断并给出理由。
3. **表述生成**：把判定结果翻译成用户能听懂的话。

**关键约束：模型不产生 `decision` 字段，只产生 `intent` 和 `category` 两个中间变量。** 最终 decision 由规则引擎根据规则与中间变量计算得出。模型没有权限给出结论，只能提供输入——这是防止模型越权的根本手段，靠架构保证而非靠 prompt 祈祷：`IntentResult` / `CategoryResult` 这两个 Pydantic 模型里**根本不存在** `decision` 和 `refund_amount` 字段。

### 6.2 冲突仲裁：为什么最终没有"仲裁层"

**已实现对冲突的处理只有一条：规则优先，且这种"冲突"在物理上不可能发生。**

因为 `judge()` 是顺序执行 + 提前 return：前序规则命中即终止，后面的规则根本执行不到。模型只提供 `intent`，不提供结论，所以不存在"模型结论与规则结论打架"这个场景——它连结论都没有。

设计阶段确实规划过更复杂的仲裁（下表，**均未落地，保留在此仅作设计记录**）：

| 设计中的情形 | 计划中的处理 | 为什么最终没做 |
|---|---|---|
| 模型判定与硬规则冲突 | 硬规则胜，记冲突日志 | 模型不产出判定结论，无冲突可记 |
| 模型判定与软规则冲突 | 模型胜，置信度压至 0.75，标记 `override` | 同上；且"软规则"这个概念在实现里没有落点 |
| 规则完全未覆盖 | 模型判定，置信度上限 0.70 | 未覆盖即 `R-504` 转人工。**让模型去填规则的空白，等于让最不可控的组件处理最边缘的场景** |
| 置信度 < 0.70 → 转人工 | 阈值拦截 | 置信度由路径推导（0.95 / 0.75 / 1.0），不存在"低置信自动结论" |

**这段保留的价值**：它记录了"想过更复杂的方案、最后判断不需要"的过程。删掉它，读者会以为设计一开始就这么简洁；留着它，才看得出**减法也是设计**。

### 6.3 咨询分支：Agent 化路径（已落地）

判定链路是确定性的，用不上自主规划；但**政策咨询分支是真正的开放式问答**——用户问"我这种情况到底能不能退"，系统需要自己决定查订单、查物流、检索政策，再组织答复。

**实现边界**：

```
Intent.POLICY_QUERY
  → core/agent.py::run_policy_agent()
  → 只读工具循环（≤6 步）
  → {"answer", "policy_refs", "tool_trace"}   # 没有 decision
```

其余 10 个判定分支完全不走 Agent，仍由 `judge()` 的优先级表执行。**`judge()` 在本次改造中一行未改**，212 条语义回归逐条零差异。

**为什么手写执行器，而不是直接用 `create_agent`**：

LangChain 1.x 移除 `AgentExecutor`，官方替代为 `langchain.agents.create_agent`；本项目按其三个契约（`max_iterations` / 中间步骤留痕 / 解析错误回灌）手写最小执行器，理由是不把执行路径建在 LangGraph 的图 / checkpointer 模型上（锁文件里的 langgraph 是 langchain 1.x 的传递依赖，执行器不 import 它），且需要自定义 `tool_trace` 字段与循环内的"必须检索、引用校验"拦截。没有升级或新增依赖：

```python
# 实际实现（简化）
llm = get_llm().bind_tools(READ_ONLY_TOOLS)
for step in range(1, max_iterations + 1):
    ai = llm.invoke(messages)
    if ai.invalid_tool_calls:        # 参数解析失败 → 回灌重试
        ...
    if not ai.tool_calls:            # 无工具调用 → 检查是否检索过
        ...
    for call in ai.tool_calls:       # 执行只读工具 → ToolMessage
        ...
```

三个契约的意义（面试常问）：

- `max_iterations=6`：防止模型在工具调用上空转；超限抛 `PolicyAgentError`，不自动给结论。
- `return_intermediate_steps=True`：对应 `tool_trace`，记录每轮 (tool, args, ok, output, refs)，是评测"工具选择是否正确"的唯一依据。
- `handle_parsing_errors=True`：把参数解析错误与不存在的工具名回灌给模型重试，而不是把异常直接甩给用户。

**只挂 4 个只读工具**：

| 工具 | 作用 |
|---|---|
| `query_order` | 订单状态、距签收天数、金额、例外原因 |
| `search_policy` | 规则库检索（BM25 + 中文字符二元组 + 规则关键词/天数提示） |
| `calc_return_window` | 无理由 7 天 / 质量退货 30 天 / 质量换货 15 天的剩余天数 |
| `check_logistics` | 物流状态、承运商、轨迹、签收争议标记 |

**没有任何写操作或退款工具**。限制写在 `READ_ONLY_TOOLS` 注册处，而不是靠 prompt 约束——模型即使被诱导，也没有可调用的资金动作。

**答复单的三条硬约束**：

1. **没有 `decision` 字段**。咨询不产生判定结论；界面只渲染答复、引用条款和工具轨迹。
2. **引用必须可核验**。答复中作为依据的 `R-xxx` 必须来自 `search_policy` 的实际返回；引用未检索到的条款（如用户设下的 `R-999`）直接拒绝该答复。
3. **失败必须显式**。未配置 Key、模型调用失败、超限、引用未检索条款，一律抛 `PolicyAgentError`，界面报错、评测记 `AGENT_ERROR`。**不降级为关键词或规则引擎假装成功。**

**评测**：33 条咨询专项用例覆盖通用规则、订单相关、未覆盖场景、反幻觉、越权诱导、工具失败与 11 个规则分支；另有 20 条公开法规/平台规则改写的问题用于检索稳健性回归。两者独立于 212 条判定基线，避免扩用例改变既有口径。指标口径是**工具调用与引用可验证性**（不是答复文本准确率）；引用精确度（`policy_refs` 相对 `expected_refs` 的收敛程度）与过度引用清单单列在报告中，只度量、不参与通过判定。

### 6.4 LangChain 组件分工（实际使用 vs 规划）

**实际实现用了 LCEL 三件套 + 原生工具调用**：

| 组件 | 使用位置 | 为什么用它而非手写 |
|---|---|---|
| `ChatOpenAI`（`langchain-openai`） | `get_llm()`，全局唯一模型入口 | 一处 `base_url` 即可在 DeepSeek / 通义 / 智谱 / OpenAI 间切换 |
| `ChatPromptTemplate` + LCEL（`\|`） | `intent_chain`、`category_chain`、`reply_chain` | 三条链职责独立，可单独构造、替换与评测 |
| `with_structured_output(..., method="function_calling")` | 意图与类目两条链 | 把 Pydantic schema 转成工具定义，结构由 API 层保证；比"prompt 要 JSON + json.loads"稳得多 |

**规划中但未使用（组件级；咨询分支本身已落地）**（列出来是为了说清边界，不是凑技术栈）：

| 组件 | 原计划用途 | 现状 |
|---|---|---|
| `PydanticOutputParser` | 结构化输出 | 被 `with_structured_output` 取代，不需要手写解析与重试 |
| `RecursiveCharacterTextSplitter` / `InMemoryVectorStore` | 政策文档切片与向量检索 | 18 条规则直接按标题正则抽取（`app.load_policy_text`），无需向量检索 |
| `AgentExecutor`（legacy） | 政策咨询分支 | LangChain 1.4.7 已移除；官方替代是 `create_agent` |
| `create_agent`（官方替代） | 政策咨询分支 | 可用，但返回 LangGraph 图，自定义 `tool_trace` 需 middleware；改为 `bind_tools` + 手写循环，见 §6.3 |
| `RunnableWithMessageHistory` | 多轮会话 | 当前单轮判定，`Ticket.round_count` 预留 |
| `BaseCallbackHandler` | token/耗时埋点 | 未接；判定单里 `model_trace` 字段已预留 |

**为什么判定链路不套 Agent**：判定过程不需要模型自主规划，规则引擎的执行顺序由优先级表决定。把它塞进 Agent 循环（无论 `AgentExecutor` 还是 `create_agent`），反而会让"模型决定调哪条规则"这种不该发生的事发生。**框架的适用边界由任务的确定性要求决定，这是主动的设计选择，不是能力限制。** 咨询分支则相反：没有固定执行顺序，必须由模型决定"先查订单还是先查物流"，这才轮到 Agent 模式。

## 七、评测方案

### 7.1 用例设计（实测口径）

共 **212 条**，两个来源：

| 层级 | 条数 | 来源 | 用途 |
|---|---|---|---|
| silver（按标签生成） | 150 | `tools/gen_orders.py` 反推构造 | 回归测试与分支覆盖 |
| manual（人工精标） | 62 | 手工编写 + 公开投诉语料改写 | 端到端评测（含意图识别）的主指标 |

按 `case_type` 分布：normal 177 / adversarial 15 / boundary 9 / colloquial 8 / mixed 3。

按期望判定分布：NEED_HUMAN 37、NEED_EVIDENCE 34、REJECT_OVERDUE 29、SUPPORT_RETURN 28、SUPPORT_EXCHANGE 27、SUPPORT_REFUND_ONLY 24、REJECT_EXEMPT_CATEGORY 22、GUIDE_REJECT_ON_DELIVERY 4、REJECT_CLOSED_ORDER 3、REJECT_DUPLICATE 2、POLICY_ANSWER 2。

**咨询专项集与判定基线分开**：`data/eval_consultation.jsonl` 33 条，覆盖 11 个规则分支、订单相关查询、规则未覆盖、反幻觉（R-999 陷阱）、越权诱导、工具失败；`data/public/eval_consultation_public.jsonl` 20 条是公开法规/平台规则的问法改写，用于检索稳健性回归。两者不并入 212 条，**避免扩用例改变既有回归口径**，也不把"同规则换问法"冒充成独立第三方基准。

> ⚠️ 早期文档写的是"gold 50 / silver 150"，与实现不符：人工精标实际 62 条，且 `source` 字段取值为 `silver` / `manual`。
> 边界样本也从规划的 12 条收敛为 9 条——**留白的地方要改，不能让文档比代码漂亮**。

### 7.2 指标定义

指标围绕一个核心问题：**判定错在哪一侧更严重？**

| 指标 | 定义 | 目标 |
|---|---|---|
| 判责准确率 | 与人工标注结论一致的占比 | ≥ 90% |
| 误赔率 | 不该退却判退的占比 | ≤ 3% |
| 误拒率 | 该退却判拒的占比 | ≤ 5% |
| 规则覆盖率 | `RULE_ONLY` 占比 | ≥ 55% |
| 退款金额误差 | 应退金额计算错误的占比 | ≤ 2% |
| 转人工准确率 | 应转人工的样本中实际转人工的比例 | ≥ 95% |
| 过度转人工率 | 本可自动判定却转人工的比例 | ≤ 12% |
| 平均单票成本 | token 消耗折算 | 相比全模型方案降低 40% |

**误赔率与误拒率是一对矛盾指标。** 放宽判定推高误赔（商家即时现金损失），收紧判定推高误拒（用户流失，延迟且不可逆）。两端代价不对称，阈值不能简单取中间值，要按类目调整。这个权衡过程是本项目最值得展开讲的工程决策。

### 7.3 已有基线

规则引擎（M1）在现有 2000 条样本上的实测：

| 数据集 | 准确率 | 说明 |
|---|---|---|
| gold 17 条 | 17/17 = 100% | 端到端（含关键词意图识别降级版） |
| silver 1986 条 | 1986/1986 = 100% | 给定正确意图，验证判定逻辑 |

这个 100% 的正确解读：**判定逻辑侧没有 bug，所有风险集中在输入侧（意图识别）。** 证据：gold 中一条"杯口崩了"的话术，因关键词表只有"崩瓷"而漏检，整条判定落到兜底转人工——判定规则没有错，错在语义理解。这决定了后续评测的重心应放在意图识别准确率上。

**为什么 M3 没有单独的 `arbitrator.py`**：最早的方案是"规则引擎输出候选结论 → 仲裁层按优先级挑一个"，实际写下来发现仲裁就是判定本身——候选结论的生成也依赖优先级（同一张单换个诉求结论就变），拆成两层只会让优先级表出现在两个地方。**少一层抽象不是偷懒，是发现这层抽象没有独立职责。** 同理，`core/chains.py` 最终并入 `core/semantics.py`：三条链共享同一套降级与来源上报逻辑，分成两个文件反而要来回跳。

**顺序原则**：语义层之前评测脚本可以先写（不依赖网络）；界面在判定单命令行正确之后才做——过早优化展示层会掩盖核心逻辑的问题。如果时间不够，砍的顺序是 M5 演示 → 表述生成链 → README 美化；M1 规则基线和 M4 评测绝对不能砍。

## 九、面试讲解要点（摘要，完整题库见 [`面试问答手册.md`](./面试问答手册.md)）

**Q1：为什么不做成聊天机器人？**
聊天机器人的产物是话术，无法审计、无法对账、无法统计准确率。判责引擎的产物是结构化判定单，可以入库抽检。前者证明会调 API，后者证明懂业务建模。

**Q2：为什么不直接让大模型判？**
四个缺陷：结论不稳定、无依据、倾向顺着用户、边界不可控。售后判责是规则密集任务，规则的确定性不能用概率模型替代。所以 Rule-first，模型只做语义补充。

**Q3：规则和模型结论冲突怎么办？**
没有"冲突"这回事——模型不产出判定结论，它只输出 `intent`，`decision` 由规则引擎独占签发。实现上是顺序执行 + 提前 return，前序规则命中即终止，两条规则物理上不可能同时生效。设计阶段确实规划过"软规则/置信度阈值"那套仲裁，实现时判断不需要，删掉了（见 §6.2）。

**Q4：置信度是模型自己说的吗？**
不是。模型自评置信度不可校准、不可复现，同一输入可能给不同数值。置信度由判定路径推导：`RULE_ONLY` = 0.95，`HUMAN` = 1.0（表达"该转人工这件事确定"，不是"结论可信"），`MODEL_ASSISTED` = 0.75 为预留值当前未启用。可复现、可单测。

**Q5：怎么证明它比人工好？**
不比"准"比"稳"。人工的一致性会随疲劳和个体差异波动，规则引擎对同一工单永远给同一结论。指标上我盯误赔率和误拒率，而不是笼统的准确率——两类错误的代价不对称。

**Q6：数据哪来的？**
规则引自消法第二十五条与平台公开规则，逐条标注编号；订单按五维场景矩阵、以"按标签生成"的方式构造，避免用被测系统生成标签的循环论证；评测语料来自公开投诉案例，脱敏后使用。**关键不是数据真不真，而是构造方法能不能说清。**

**Q7：数据量这么少能说明什么？**
这是固定评测集，不是训练集，作用是回归验证而非统计显著性。**但准确说是 212 条评测用例 + 2000 条订单 + 13,800 组矩阵组合，别把三个数字混着讲**——被追问时混讲会显得没跑过。

**Q8：这个项目最大的技术难点？**
不是调通模型，是**给不确定性划边界**。哪些判定必须确定性、哪些可以容忍概率、冲突时谁让步——这套边界设计决定了系统能不能用。

## 十、环境与运行

```bash
# 1) 建项目内独立环境（--copies 复制解释器，宿主 Python 被替换时依赖不丢）
python -m venv --copies .venv
.venv/Scripts/python.exe -m pip install -r requirements-lock.txt --index-url https://pypi.org/simple

# 2) 模型配置（写在项目根 .env，任选一家 OpenAI 兼容服务）
#    ECOM_LLM_API_KEY=sk-xxx
#    ECOM_LLM_BASE_URL=https://api.deepseek.com/v1
#    ECOM_LLM_MODEL=deepseek-chat

# 3) 运行（前四条不需要 API Key）
.venv/Scripts/python.exe -m core.rules                 # 规则引擎 gold 校验 17 条
.venv/Scripts/python.exe -m eval.audit_matrix          # 矩阵审计 13,800 组合
.venv/Scripts/python.exe -m eval.run_eval              # 关键词基线评测（212 条）
.venv/Scripts/python.exe -m eval.run_eval --semantic   # 语义层评测（需 Key，约 3-5 分钟）
./start.bat                                            # Windows 双击启动界面
.venv/Scripts/python.exe tools/launch.py --restart     # 命令行启动（自动选解释器 + 查端口）
```

时间基准：订单数据以 2026-10-28 12:00 为基准构造。系统固定该基准时间（可用环境变量 `ECOM_REFERENCE_NOW` 覆盖），否则数据会随时间推移"腐化"——所有订单逐渐超期，七天无理由判定全部失效。

> 环境变量是 `ECOM_LLM_*` 而不是 `OPENAI_*`：`semantics.py` 里有自己的 `_load_dotenv()`，
> 只认项目自己的前缀，避免和机器上其他项目的 `OPENAI_API_KEY` 串味。
