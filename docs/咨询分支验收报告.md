## 四、失败必须显式，不许假装成功

| 场景 | 实际行为 | 证据 |
|---|---|---|
| 未配置 Key | 抛 `PolicyAgentError`，评测整体不可用，退出码 1 | `python -m eval.run_eval --consultation` → `退出码 1` |
| 未配置 Key（CLI） | 打印 `[咨询路径不可用]`，退出码 2 | `python -m core.agent "..."` → `退出码 2` |
| 模型调用失败 | 抛 `PolicyAgentError`，评测记 `AGENT_ERROR`，附失败前 `tool_trace` | 首轮 C002 遇到 `Connection error`，报告如实记 "失败"，未用兜底话术冒充通过 |
| 引用未检索条款 | 先回灌补检索/删编号；仍不合规则抛错，拒绝答复 | `core/agent.py` 的 `unverified` 分支 |
| 未检索就作答 | 提醒一次；仍不检索则抛错 | `core/agent.py` 的 `search_policy not in called_tools` 分支 |
| 超过 6 步 | 抛错，转人工，不自动给结论 | `max_iterations` 的 `for...else` |

**关于首轮 C002 的说明**：最早一轮 33 条中，C002 在第一次模型调用时遇到 `Connection error`，报告把它记为失败，`tool_trace` 为空，没有降级、没有套用关键词答案。后续复跑通过（本报告 20:58 这次 C002 调了 2 次 `search_policy`，通过）。这里保留这段记录，是为了说明"失败会被如实记录"，而不是掩盖一次网络错误。

**如实写进已知限制**：

- **口径变化要单独说**：v2 把"引用"与"提及"分开了，正文照常解释背景条款，但不再计入 `policy_refs`。所以 57.8% 相对 41.9% 的提升里，有一部分是度量口径变清楚，不能全算成模型变准。真正可比的是同一口径下的两次 v2 运行（57.8% / 63.4%）。
- `expected_refs` 只标了必须命中的主条款，剩余 13 条额外引用里仍有上下文相关条款（问七天无理由附带例外类目、运费承担），不等于错误。因此这是**引用收敛度**，不是引用错误率。真正驳回的是：引用未检索到的条款、漏掉 `expected_refs`、把禁止条款当依据——仍按失败处理。
- **继续压的代价**：再要求模型只报一条，会开始漏引（R-102/R-301 这类例外与运费条款对用户是有效信息）。漏引是合规风险，多引只是体验问题，故停在 v2。
- 212 条判定基线与咨询集独立；v2 只改咨询路径提示词与 `policy_refs` 取值，`judge()` 未改，全量复跑逐条差异见第一节。
