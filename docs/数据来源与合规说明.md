# 数据来源与合规说明

> 这份文档回答三个问题：仓库里的数据从哪来、能不能公开、为什么没有直接抓投诉站。
> 面试被追问数据时，先讲这张表，再讲取舍。

## 一、结论先行

**仓库内不包含任何抓取的用户投诉原文，也不包含真实姓名、手机号、地址、订单号。**

数据分三类：

| 类别 | 生成方式 | 是否含真实个人信息 | 能否随仓库分发 |
|---|---|---|---|
| 订单数据（1,986 条） | 按标签合成 | 否 | 是 |
| 评测话术（212 + 33 条） | 人工编写 / 按标签构造 | 否 | 是 |
| 公开规则改写（20 条） | 依据公开法律法规与平台规则改写问题 | 否 | 是，需标注来源 |

**没有做的事**：没有批量抓取黑猫投诉、12315 公示、电商平台评论区，也没有把公开客服对话数据集整包塞进仓库。原因见第三节。

## 二、数据清单

| 文件 | 条数 | 性质 | 来源与依据 | 许可 / 分发 |
|---|---|---|---|---|
| `data/policies.md` | 18 条规则 | 规则库 | 《消费者权益保护法》第 24/25 条、《电子商务法》第 50 条、《民法典》第 566 条；平台售后/交易/退款规则的公开口径 | 公共法律文本 + 本项目改写；可分发 |
| `data/orders.json` | 17 | gold 订单 | `tools/label_gold.py` 人工确认，覆盖 11 个判定分支 | 合成数据；可分发 |
| `data/orders_bulk.json` | 1986 | silver 订单 | `tools/gen_orders.py` 按标签反推构造（label-first） | 合成数据；可分发 |
| `data/eval_cases.jsonl` | 212 | 判定评测 | 150 条按标签生成 + 62 条人工编写/改写 | 本项目编写；可分发 |
| `data/eval_consultation.jsonl` | 33 | 咨询 Agent 评测 | 人工编写，覆盖通用规则、订单相关、未覆盖、反幻觉、越权、工具失败、规则分支 | 本项目编写；可分发 |
| `data/public/seed_consultation_public.raw.jsonl` | 20 | 公开规则改写种子 | 以公开法律法规和平台规则公开条款为依据改写问题，**不是原文抓取** | 改写文本；可分发，保留来源字段 |

| `data/public/import_manifest.jsonl` | 1 行/批 | 导入记账 | 输入文件 SHA-256、保留/丢弃条数、脱敏命中数、case_id 列表 | 审计用；可分发 |

> 口径提醒：**1,986 条订单（口语可说约 2000 条）、212 条判定用例、33 + 20 条咨询用例、13,800 组矩阵组合，是四个不同的数字**，不要混着讲。

## 三、为什么没有直接抓投诉站

不是"没想到"，是评估后主动放弃：

| 风险 | 具体说明 |
|---|---|
| 平台条款 | 黑猫投诉、12315 公示、电商评论区通常禁止批量抓取与再分发；抓取本身可能违反 ToS |
| 个人信息 | 投诉文本常含姓名、手机号、地址、订单截图；即使删字段，正文里仍可能有 |
| 著作权 | 用户生成内容不当然允许转载；整段复制进开源仓库风险更高 |
| 反爬与稳定性 | 抓取脚本依赖页面结构，几个月后必坏；无法作为可复现的数据管线 |
| 评测污染 | 投诉文本的情绪表达与售后判责口径不一致，直接当"标准答案"会引入噪声 |

**合规的替代做法**（本项目采用）：

1. **用公开法律文本做依据**：法条是公开的，引用并改写不涉及用户隐私。
2. **用平台公开规则做规则源**：只提取规则口径，不复制用户内容。
3. **问题自己写、标注自己打**：话术覆盖真实表达方式，但不冒充"真实工单"。
4. **外部数据只走导入器**：来源、许可、SHA-256、脱敏、去重全部记账，不直接复制。

|---|---|---|---|

| 淘宝客服对话（2018 公开版） | 真实电商客服会话 | 以原始发布方声明为准 | 未分发 |
| CSDS（中文客服对话摘要） | 电商客服对话 + 摘要标注 | 以仓库 LICENSE 为准 | 未分发 |
| CCSE-CS | 中文客服共情对话，含电商场景 | 以仓库 LICENSE 为准；部分为模型生成 | 未分发 |
| ECOD（电商订单纠纷） | 评价 + 商家回应 + 裁决标签 | 学术使用；以 Mendeley/Springer 条款为准 | 未分发 |
| InfiniFlow 电商客服工作流 | 客服对话 + 业务工作流节点 | 以 Hugging Face 数据集页标注为准 | 未分发；页面当前网络不可达，未核验 |

**为什么不在仓库里放"公开数据集样本"**：这些数据集的许可多为研究用途，允许"使用"不等于允许"再分发"；把样本复制进公开仓库，等于替发布方做了一次再许可。正确做法是提供导入器和使用说明，由使用者自行下载并确认许可。

## 五、导入流程（可复现）

外部数据统一走 `tools/import_public_cases.py`，不手工改 JSONL：

```bash
# 1. 准备原始 JSONL（一行一条，字段见脚本 docstring）
# 2. 先 dry-run：只校验，不写文件
python tools/import_public_cases.py \
  --input raw.jsonl \
  --output data/public/eval_consultation_public.jsonl \
  --kind consultation \
  --source-name "数据集名称" \
  --source-url "https://..." \
  --license "许可证标识" \
  --source-type public_dataset \
  --dry-run

# 3. 确认无误后去掉 --dry-run 落盘
```

脚本做四件事：

| 步骤 | 行为 |
|---|---|
| 校验 | `expected_decision` 必须是合法枚举；`expected_refs` 必须是 `R-xxx` 且真实存在于 `policies.md`；判定类必须有 `order_id` |
| 脱敏 | 手机号、身份证、银行卡、邮箱、详细地址替换为 `<PHONE>` / `<ID>` / `<BANK>` / `<EMAIL>` / `<ADDR>` |
| 去重 | 去空白、去标点、转小写后与 212 条、33 条及本批已导入记录比对 |
| 记账 | 输入 SHA-256、保留/丢弃条数、脱敏命中数、case_id 写入 `import_manifest.jsonl` |

**脱敏后内容过短或几乎全是占位符的记录会被丢弃**——隐私文本没有评测价值。

## 六、这 20 条公开改写数据怎么用

它们**不并入 212 条判定基线**，单独跑：

```bash
# 33 条主咨询集（默认）
python -m eval.run_eval --consultation

# 20 条公开改写集，报告写到 eval/report-consultation-public.md
python -m eval.run_eval --consultation \
  --consultation-cases data/public/eval_consultation_public.jsonl \
  --consultation-tag consultation-public
```

用途是**检索稳健性回归**：同一规则换一种问法，检查 `search_policy` 是否还能召回正确条款。它**不是独立第三方基准**——期望条款仍来自本仓库规则库，不能拿它宣称"外部数据准确率"。

## 八、面试口径

**不要说**："我爬了十万条投诉数据。"
**应该说**：

> 订单是按标签合成的，1,986 条（约 2000），覆盖 11 个判定分支；评测话术 212 条，其中 62 条人工精写；咨询分支另有 33 条专项用例和 20 条公开法规改写。没有抓投诉站——ToS、隐私和再分发许可都过不去。外部数据我做了导入器：校验、脱敏、去重、SHA-256 记账，来源和许可都能查。数据规模不是卖点，**标注口径和可复现性才是**。
