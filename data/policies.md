# 电商售后判责规则库

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 生效日期 | 2025-07-28 |
| 适用范围 | 平台自营及入驻商家的实物类商品售后判责 |
| 文档性质 | 判责引擎的唯一规则依据，代码中的每条判定必须引用本文编号 |

---

## 零、术语与计算口径

为避免实现歧义，先固定几个口径。**规则引擎的所有时限计算必须以此为准。**

- **签收日**：以物流轨迹最后一条"已签收"记录的时间为准。无签收记录视为未签收。
- **距签收天数**：签收当日记为第 0 天，次日为第 1 天。例：10 月 26 日签收，10 月 28 日提出申请，距签收天数为 2 天。
- **自然日**：含周末与法定节假日，不另行顺延。
- **商品完好**：商品本体、配件、吊牌、包装完整，不影响二次销售。已拆封不必然等于不完好，需结合类目判断。
- **例外类目**：见 R-102 列明的类目清单，该类目不适用七天无理由退货。
- **大额订单**：单笔实付金额大于等于 2000 元。

## 一、总则：判定优先级

当多条规则同时可能适用时，按以下顺序仲裁。**优先级在前的规则一旦命中，直接采纳其结论，不再进入后续规则。**

| 优先序 | 规则 | 说明 |
|---|---|---|
| 1 | R-601 政策咨询 | 只问规则、未提出执行诉求 → 不产生判定，交咨询链路作答 |
| 2 | R-501 幂等约束 | 已退款或已有进行中工单的订单，不再进入任何判定 |
| 3 | R-502 已关闭订单 | 已取消 / 交易关闭 / 待付款的订单无售后标的，不再进入任何判定 |
| 4 | R-505 金额异常 | 实付金额缺失或为 0，无法计算任何退款金额，直接转人工 |
| 5 | R-402 大额阈值 | 金额达标的订单一律转人工，不论其他规则结论 |
| 6 | R-503 物流争议 | 签收事实存疑时，不适用任何实体退货规则 |
| 7 | R-102 例外类目 | 例外类目不适用无理由退货，优先于 R-101 |
| 8 | R-201 / R-202 未发货与在途 | 未签收订单走独立路径，不适用签收类时限规则 |
| 9 | R-105 超期拒收 | 距签收 > 30 日的，不再受理 |
| 10 | R-103 / R-104 质量问题 | 质量问题的时限长于无理由，优先于 R-101 适用 |
| 11 | R-101 七天无理由 | 距签收 ≤ 7 日的标准退货路径 |
| 12 | R-106 超无理由期 | 距签收 8–30 日的无理由主张不再支持，质量问题仍可申请 |
| 13 | R-301 运费承担 | 不独立产生结论，仅在前述规则确定结论后附加 |

**设计说明（三条，都源于同一个原则：先确认"能不能判"，再判断"该怎么判"）：**

1. **R-601 政策咨询置于最前**：咨询不触发任何账务动作。若被幂等、超期等规则拦下，问一句"退货流程怎么走"却得到"拒绝受理"的答复，是明显的错答。
2. **R-501 / R-502 次之**："有没有可退的东西"先于"该不该退"。已退款属账务正确性问题，已取消/待付款属标的不存在——两者都不应进入任何判定路径。
3. **R-503 物流争议优先于实体规则**：退货规则的前提是"商品已在用户手中"，这一事实有争议时，讨论能不能退没有意义，先核实事实。

**另一条容易漏的约束**：R-201（未发货直接退款）要求意图明确。**退款是资金动作，意图不明时不得自动执行**——用户说"帮我处理一下这个订单"，系统不能替他决定退款。

## 二、退货时限与条件

### R-101 七天无理由退货

- **依据**：《中华人民共和国消费者权益保护法》第二十五条；平台《售后服务规则》第 3.1 条
- **适用条件**（须全部满足）：
  1. 订单状态为「已签收」
  2. 距签收天数 ≤ 7
  3. 商品不属于 R-102 列明的例外类目
  4. 商品完好，不影响二次销售
- **判定结果**：`SUPPORT_RETURN`
- **运费承担**：买家（见 R-301）
- **可退金额**：订单实付金额，不含已使用的优惠券与积分抵扣
- **不适用情形**：商品存在质量问题的，改按 R-103 处理（时限更长，对用户更有利）

> 实现提示：本条与 R-103 的区分点是「用户主张的原因」。用户主张"不喜欢/不想要/买错了"归入本条；主张"破损/开胶/故障/与描述不符"归入 R-103。

### R-102 不适用七天无理由的例外类目

- **依据**：《消费者权益保护法》第二十五条第一款所列除外情形；平台《类目售后规则》附录 A
- **例外类目清单**：

| 类目 | 例外原因 | 判定依据字段 |
|---|---|---|
| 生鲜果蔬、冷藏冷冻 | 易腐变质，退货后无法二次销售 | `is_fresh = true` |
| 定制礼品、刻字印刷 | 按用户要求定制，无法二次销售 | `is_custom = true` |
| 个护美妆（已拆封） | 涉及卫生，拆封后不可退 | `sealed = false` |
| 数码产品（已激活） | 激活后影响二次销售 | `exempt_reason = 已激活` |
| 内衣、袜类等贴身衣物 | 涉及卫生 | `exempt_reason = 贴身衣物` |

- **判定结果**：`REJECT_EXEMPT_CATEGORY`
- **重要约束**：例外类目**仍适用质量问题退换**。用户主张质量问题的，不适用本条，改按 R-103 处理。
- **重要约束**：本条优先于 R-101。即便距签收仅 0 天，例外类目的无理由退货申请仍应拒绝。

### R-103 质量问题退货

- **依据**：《消费者权益保护法》第二十四条；平台《售后服务规则》第 3.4 条
- **适用条件**：
  1. 订单状态为「已签收」
  2. 距签收天数 ≤ 30
  3. 用户主张商品存在质量问题（破损、功能故障、与描述不符、缺件等）
  4. 用户已提供或可提供凭证（照片、视频、检测报告）
- **判定结果**：
  - 已提供凭证：`SUPPORT_RETURN`
  - 未提供凭证：`NEED_EVIDENCE`，引导补充凭证后重新判定
- **运费承担**：卖家（见 R-301）
- **不适用本条**：距签收 > 30 天的，按 R-105 处理

> 实现提示：凭证是否已提供，由工单的 `evidence_provided` 字段判定，不由模型从文本推断。模型只能判断"用户主张的是不是质量问题"，不能判断"凭证是否充分"。

### R-104 质量问题换货

- **依据**：平台《售后服务规则》第 3.5 条
- **适用条件**：
  1. 订单状态为「已签收」
  2. 距签收天数 ≤ 15
  3. 用户明确要求换货而非退货
  4. 同款商品有库存
- **判定结果**：`SUPPORT_EXCHANGE`
- **运费承担**：卖家
- **与 R-103 的关系**：二者时限不同（换货 15 天、退货 30 天）。距签收在 16–30 天之间的质量问题，只能退货不能换货。

### R-105 超期不再受理

- **依据**：平台《售后服务规则》第 3.6 条
- **适用条件**：
  1. 距签收天数 > 30
  2. 不存在法律规定的特殊情形（如商品存在危及人身安全缺陷）
- **判定结果**：`REJECT_OVERDUE`
- **说明**：超过 30 天后，无论主张无理由还是质量问题，均不再受理。用户可通过投诉渠道另行申诉。
- **例外**：商品存在危及人身、财产安全缺陷的，不受本条限制，一律 `NEED_HUMAN` 处理。

### R-106 已过无理由期、未过受理期

- **依据**：平台《售后服务规则》第 3.2 条（无理由退货限于签收后 7 日内）
- **适用条件**：距签收天数在 8–30 日之间，且用户主张的是**无理由**（不喜欢/不想要/拍错）
- **判定结果**：`REJECT_OVERDUE`
- **说明**：七天无理由是一项**有期限**的权利，过期即不再支持，与"30 日受理期"是两回事——30 日受理期是质量问题退货的窗口。此档必须明确拒绝，不能因为"还没超过 30 天"就误判为可退。
- **与其他规则的关系**：若同一订单用户主张质量问题（R-103/R-104），仍按质量路径处理，不受本条限制。

## 三、按订单状态的独立路径

### R-201 未发货订单取消

- **依据**：平台《交易规则》第 5.2 条
- **适用条件**：订单状态为「待发货」，尚未产生物流单号
- **判定结果**：`SUPPORT_REFUND_ONLY`，全额退款，无需退货
- **运费承担**：无
- **前置条件（重要）**：**用户诉求必须明确**（取消 / 不想要 / 未收到）。若无法识别用户意图，不得自动退款——退款是资金动作，不能在诉求不明的情况下替用户执行。此时按 R-504 转人工。
- **说明**：未发货订单用户有权无条件取消，不受七天限制，不受类目限制。

### R-202 运输在途订单

- **依据**：平台《交易规则》第 5.3 条
- **适用条件**：订单状态为「已发货」，物流显示在途未签收，**且用户提出了退货 / 退款 / 拒收诉求**
- **判定结果**：`GUIDE_REJECT_ON_DELIVERY`，引导用户拒收，拒收后退款
- **前置条件（重要）**：与 R-201 同一原则——不替用户产生账务动作。在途状态下用户说"快递到哪了""能开发票吗"并不包含退货意思，此时不得回复"建议拒收、全额退款"，应按 R-504 转物流客服答复。退货意愿的判定口径：意图为无理由/质量问题，或工单文本明确出现退货/退款/拒收字样，二者满足其一即视为要退。
- **说明**：
  - 在途订单**不可修改收货地址**（地址变更需联系承运商，平台无法操作）
  - 用户可拒收，包裹退回仓库后 1–3 个工作日退款
  - 生鲜类在途订单拒收可能产生损耗，需在话术中提示
- **运费承担**：无理由拒收由买家承担退回运费；商品破损导致的拒收由卖家承担（见 R-301）

### R-203 已签收订单

- **依据**：平台《售后服务规则》第 3.1 条
- **适用条件**：订单状态为「已签收」
- **判定结果**：不独立产生结论，进入 R-101 / R-102 / R-103 / R-105 判定

## 四、费用与时效

### R-301 运费承担

- **依据**：平台《售后服务规则》第 4.2 条
- **规则**：
  | 退货原因 | 寄回运费 | 说明 |
  |---|---|---|
  | 七天无理由 | 买家承担 | 若订单含运费险，由保险赔付 |
  | 质量问题 | 卖家承担 | 用户先垫付的，退款时一并返还 |
  | 卖家发错货/漏发 | 卖家承担 | 全额退款并补偿运费 |
  | 未发货取消 | 无运费 | 不产生物流 |
- **判定结果**：不独立产生结论，作为 `shipping_bearer` 字段附加在判定单上

### R-401 退款到账时效

- **依据**：平台《退款服务规范》第 2.1 条
- **规则**：
  - 仓库验收通过后 1–3 个工作日发起退款
  - 微信支付、支付宝：原路退回，1–3 个工作日到账
  - 银行卡：3–7 个工作日到账
  - 余额：实时到账
- **说明**：本条为说明性规则，不参与判定，仅用于生成回复话术

## 五、风控与约束

### R-505 金额异常：无法计算退款金额

- **依据**：账务一致性要求（判定单自校验不变量：支持类的退款金额必须为正数）
- **适用条件**：订单实付金额缺失、为 0 或为负
- **判定结果**：`NEED_HUMAN`
- **重要约束**：本条位于 R-402 之前。一张 0 元订单若进入实体规则，会产出"支持退货 0.00 元"这种自相矛盾的判定单——结论看着是支持，实际无款可退。
- **理由**：金额是判决的输出参数之一，不是判决的前提。参数本身不可用时，任何结论都无法落地，只能先补事实。

### R-402 大额订单强制人工复核

- **依据**：平台《资金风控规范》第 6.1 条（内部规则）
- **适用条件**：单笔实付金额 ≥ 2000 元
- **判定结果**：`NEED_HUMAN`
- **重要约束**：本条排在"能不能判"的规则（R-601/R-501/R-502/R-505）之后、"该怎么判"的规则之前。**即便其他实体规则明确支持退货，只要金额达标，一律转人工**，不允许系统自动给出退款承诺。
- **理由**：大额退款的欺诈风险与资金损失不可逆，必须由人工核验商品状态与用户历史。

### R-501 幂等约束：不可重复受理

- **依据**：平台《售后服务规则》第 6.3 条；账务一致性要求
- **适用条件**（满足任一）：
  1. 订单状态为「已退款」
  2. 订单已存在状态为「处理中」或「已完成」的售后工单
- **判定结果**：`REJECT_DUPLICATE`
- **说明**：账务正确性优先于业务判断。已退款的订单不再进入任何判定路径，直接拒绝并提示用户查询退款进度。
- **例外**：同一订单的**不同商品**可分别申请售后，需以 SKU 维度判断，而非订单维度。

### R-503 物流争议：签收事实存疑

- **依据**：《电子商务法》第 50 条（快递物流服务提供方应提供签收凭证）；平台《物流纠纷处理规范》
- **适用条件**：订单已显示签收，但用户主张未收到货（虚假签收、代收争议、物流轨迹与签收记录冲突）
- **判定结果**：`NEED_HUMAN`
- **说明**：退货规则的适用前提是"商品已在用户手中"。当这一事实本身存在争议时，讨论能不能退没有意义——先要确认货在哪。此类纠纷需要调取签收底单、派送员证词，属于人工核实范围，系统不得自行给出退或不退的结论。
- **不与 R-202 混淆**：在途（未签收）状态下用户说"不想要了"，货仍在可控范围内，引导拒收即可；只有**已签收却被否认**才构成事实争议。

### R-502 已关闭订单：不存在售后标的

- **依据**：《中华人民共和国民法典》第 566 条（合同解除后，尚未履行的终止履行）；平台通用规则
- **适用条件**（均无可退标的，属同一等价类）：
  1. 订单状态为「待付款」（未支付，无款可退）
  2. 订单状态为「已取消」或「交易关闭」（含超时未支付关闭）
- **判定结果**：`REJECT_CLOSED_ORDER`
- **说明**：待付款订单未发生支付，无款可退；订单取消即买卖合同已解除，不存在可退的商品标的——两类情形售后流程均无从成立。已扣款的取消订单应引导用户查询原支付渠道的退款进度，而非在本系统内新建售后工单。
- **等价类归并**：平台的「已取消」「交易关闭」「超时关闭」在售后判定上行为一致，统一归并为一个等价类，不单独建模——**状态数量由"是否产生不同判定行为"决定，不由平台状态机字段决定**。

## 六、不产生判定结论的两种情形

### R-601 政策咨询：不进入判定

- **依据**：咨询与执行是两类不同的请求。咨询只回答规则本身，不对具体订单作出结论。
- **适用条件**：用户仅询问退换货规则、流程、时限、运费由谁承担，未对某一订单提出执行诉求
  - 例："退货流程怎么走"、"七天无理由是什么意思"、"质量问题退货运费谁出"
  - 反例："我要退货"（有执行诉求）、"这单能退吗"（指向具体订单，属执行诉求）
- **判定结果**：`POLICY_ANSWER`（不产生判定结论，不挂退款金额）
- **说明**：若把咨询当诉求处理，会出现"问一句流程，得到一份拒绝受理单"的荒谬结果。咨询应由知识检索链路依据本文件作答，判定链路直接放行。
- **非终态**：用户问完规则后可继续提出执行诉求，届时重新判定。

---

### R-504 兜底：强制转人工

以下情形不适用上述任何实体规则，一律判定 `NEED_HUMAN`：

1. 单笔金额 ≥ 2000 元（R-402）
2. 用户明确要求投诉、要求平台介入、提及法律途径
3. 用户连续两轮未能提供有效订单信息
4. 商品涉及人身安全缺陷
5. 规则未覆盖的新情形（如跨境保税商品的特殊退换）
6. 工具查询失败且重试后仍失败

- **判定结果**：`NEED_HUMAN`
- **说明**：R-504 是兜底条款。**宁可多转人工，也不能错判**——赔付成本是即时可见的，信任成本是延迟且不可逆的，两者代价不对称。任何无法确定映射到具体规则的诉求，一律移交人工，而不是让系统给出一个看似合理但无依据的结论。
